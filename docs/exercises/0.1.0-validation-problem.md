# Exercício 0.1.0 — Problem de validação

## Objetivo
Implementar `ValidationProblemFactory.fromViolations`, que transforma as
violações do Hibernate Validator no corpo de erro padrão da API (ADR-0004).

Arquivo: `finator-commons/src/main/java/dev/trocolis/finator/commons/problem/ValidationProblemFactory.java`

## Regras
1. `violations` nulo ou vazio lança `IllegalArgumentException`.
2. `type`, `title` e `status` vêm de `ProblemType.VALIDATION`.
3. Cada violação vira um `FieldViolation(field, message)`. O campo é o **último
   nome** do caminho da violação: `create.request.email` vira `email`.
4. A lista sai **ordenada por campo** e, dentro do mesmo campo, **por mensagem**.
   A ordem precisa ser estável porque `Set` não tem ordem definida, e o app e os
   testes não podem depender da sorte.
5. `detail` conta os **campos distintos**: `"1 campo inválido"` ou
   `"3 campos inválidos"`. Um campo com duas violações conta uma vez só.

## Testes
- `ValidationProblemFactoryTest`: as regras acima, uma a uma.
- `ProblemExceptionMappersTest#invalidRequestReturnsValidationProblem`: o fluxo
  completo, de uma requisição HTTP inválida até o JSON de resposta.

```bash
./mvnw test -Pexercises -pl finator-commons
```

## Conceitos praticados
- **Streams**: `map`, `sorted`, `distinct`, `count`, `toList`.
- **Comparator composto**: `Comparator.comparing(...).thenComparing(...)`.
- **Iterable**: `jakarta.validation.Path` é um `Iterable<Path.Node>`; nem todo
  nó tem nome (um nó de parâmetro de método tem, um nó de elemento de lista
  pode não ter).
- **Imutabilidade**: o que o `toList()` devolve é imutável. Veja também o que o
  construtor compacto de `Problem` faz com a lista.
- **Generics com curinga**: por que o parâmetro é `Set<? extends ConstraintViolation<?>>`
  e não `Set<ConstraintViolation<Object>>`? (Dica: tente passar um
  `Set<ConstraintViolation<Customer>>` para a segunda versão.)
