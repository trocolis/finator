# 0.1.0 — Fundação

Objetivo do escopo: deixar pronta a base técnica sobre a qual todos os serviços
serão construídos, sem nenhuma regra de negócio ainda.

## Histórias

### FIN-001 — Monorepo multi-módulo
**Como** desenvolvedor, **quero** um único repositório com um módulo Maven por
serviço, **para** compilar, testar e versionar tudo junto.

Critérios de aceite:
- [ ] `./mvnw verify` na raiz compila e testa todos os módulos.
- [ ] Java 25 e a versão do Quarkus são definidos em um só lugar (parent pom).
- [ ] O Maven Wrapper dispensa ter o Maven instalado.

Estimativa: 2 h

### FIN-002 — Esqueleto do identity-service e do ledger-service
**Como** operador, **quero** que cada serviço suba com health checks,
contrato OpenAPI e migrações de banco, **para** saber se ele está pronto para
receber tráfego.

Critérios de aceite:
- [ ] `GET /q/health/live` responde `UP` enquanto o processo está saudável.
- [ ] `GET /q/health/ready` inclui a verificação da conexão com o banco.
- [ ] Sem a configuração obrigatória, o serviço não sobe e informa o que falta.
- [ ] `GET /q/openapi` publica o contrato do serviço.
- [ ] O Flyway executa as migrações na inicialização.
- [ ] Profiles `dev`, `test` e `prod` com configuração própria; nenhum endereço
      ou senha fica no código, tudo vem de variáveis de ambiente.

Estimativa: 3 h

### FIN-003 — Erros padronizados (RFC 9457)
**Como** desenvolvedor do app mobile, **quero** que todo erro da API tenha o
mesmo formato, **para** tratar falhas de um jeito só.

Critérios de aceite:
- [ ] Respostas de erro usam `application/problem+json`.
- [ ] Erros de validação listam cada campo inválido e a mensagem.
- [ ] Erros inesperados devolvem 500 sem expor stack trace nem detalhes internos.

Estimativa: 3 h (inclui o exercício da versão)

### FIN-004 — Integração contínua e imagem de container
**Como** revisor de PR, **quero** que cada push rode build e testes
automaticamente, **para** só revisar código que compila e passa nos testes.

Critérios de aceite:
- [ ] Workflow do GitHub Actions roda `./mvnw verify` em pushes e PRs.
- [ ] Cada serviço tem um Dockerfile JVM que roda como usuário não-root.

Estimativa: 1 h

### FIN-005 — Bancos de dados por serviço
**Como** operador, **quero** um script que crie um banco e um usuário para cada
serviço, **para** que um serviço não consiga ler os dados do outro.

Critérios de aceite:
- [ ] Script SQL idempotente, sem senhas embutidas (recebidas como variáveis do `psql`).

Estimativa: 0,5 h

## Total estimado: 9,5 h

## Notas de implementação
- **Datasource desativado em silêncio.** Quando a URL do banco referencia uma
  variável de ambiente inexistente, o Quarkus 3.40 não falha: trata o datasource
  como não configurado, pula o Flyway e o readiness responde `UP`. Descobrimos
  isso subindo o jar sem `.env`. A correção foi o `RequiredConfigCheck` no
  `finator-commons`, que aborta a inicialização listando o que falta.
  Lição: um health check verde não prova que a configuração está certa.
